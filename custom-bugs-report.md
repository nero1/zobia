**Report generated:** Friday, July 03, 2026 — 05:05 PM UTC
**Scope:** `apps/android` (Capacitor Android app) as primary target, cross-referenced against `apps/web` (Next.js web app + PWA) for feature-parity gaps, plus `shared/` and CI/build config. `apps/expo` was explicitly excluded (discontinued). CRON-frequency items were ignored per instructions.

## Full list of bugs found (one-line summary)

1. **ZSB-01 (Security):** Registration screen uses the insecure `zobia://` custom-scheme OAuth callback that Login was specifically patched away from (BUG-CAP-04), reopening an OAuth-code-interception window for every new sign-up.
2. **ZSB-02 (Critical — Web/PWA):** The web Creator Dashboard page reads field names that don't exist in its own API response, so `data.revenueStreams.map(...)` throws and the entire page crashes for every creator.
3. **ZSB-03 (High):** The API client's "unauthenticated" event system is fully wired up but has zero subscribers, and the stale in-memory token is never cleared on refresh failure — users can get stuck in a silently-broken "looks logged in, nothing loads" state with no auto-logout.
4. **ZSB-04 (High):** Every "open in browser" bridge to an authenticated web page (KYC, creator bank account, creator wallet, admin KYC review, resume/play a game) opens with no session at all, because the mobile OAuth flow intentionally never sets browser cookies.
5. **ZSB-05 (High):** Push notification registration never re-fires after a logout because the `initialized` latch in `lib/push/index.ts` is never reset, and there is no server-side token unregister call on logout — a second account signed into the same device can miss push or receive the previous account's pushes.
6. **ZSB-06 (High):** `VITE_REALTIME_PROVIDER`/`VITE_ABLY_API_KEY` are never set in the Android CI build workflow, so every shipped APK/AAB defaults to `'none'` and Ably realtime (instant room/DM updates) is silently disabled in production, always falling back to polling.
7. **ZSB-07 (Medium-High):** The 2FA verify screen never persists the `refreshToken` the server returns, so 2FA-enabled users on Android get logged out far more often than everyone else once their access token expires.
8. **ZSB-08 (Medium):** `apiFetch.ts`'s 401-retry path silently drops the request on refresh failure without clearing the cached token or notifying anyone — a second, divergent implementation of the same broken pattern as ZSB-03.
9. **ZSB-09 (Medium):** The ad-event queue (`adEventQueue.ts`) does an unguarded read-modify-write of its IndexedDB queue; concurrent ad impressions/clicks can race and silently drop queued events.
10. **ZSB-10 (Medium):** `friends.tsx`'s accept/reject request handler reads the shared mutation hook's `.variables` instead of its own callback argument, so concurrent accept/decline actions can read the wrong action and skip/incorrectly trigger a friends-list refresh.
11. **ZSB-11 (Medium):** Spending coins (sending a gift, unlocking a sticker pack) never invalidates the shared `users/me` balance query, so the Wallet screen / balance displays elsewhere can show a stale, pre-spend coin balance.
12. **ZSB-12 (Medium):** Buying coins/stars via Google Play on the Wallet screen refreshes the balance but never invalidates the transaction-history query, so the new purchase doesn't appear in the list until an unrelated refetch happens.
13. **ZSB-13 (Medium):** The Android referral-code capture (`lib/deeplinks/referral.ts`) never expires, unlike the web/PWA's 30-day cookie/localStorage TTL — a referral tapped a year ago can still attribute a signup today.
14. **ZSB-14 (Medium):** `applyStoredLanguagePref()` — the durable, Capacitor-Preferences-backed language restore meant to survive a WebView storage clear — is fully implemented but never called from anywhere, so it can never actually run.
15. **ZSB-15 (Low-Medium):** `VITE_ABLY_API_KEY` is defined and parsed in `env.ts` but never read anywhere — dead configuration that, if ever wired up carelessly, would ship a secret Ably key inside the public client bundle (Vite exposes all `VITE_`-prefixed vars to the client).
16. **ZSB-16 (Medium — parity):** The Android notifications list only marks a notification read on tap; it has no tap-to-navigate behaviour at all, unlike the web list which links via `notification.actionUrl`.
17. **ZSB-17 (Medium — parity):** The web/PWA service worker has no Web Push implementation whatsoever (no `push` event handler), so PWA users get zero background push notifications while Android (FCM) does.
18. **ZSB-18 (Medium — parity/i18n):** The entire Business Ads Hub + Business Pages screens on Android are hardcoded English with no `useTranslation`/`t()` usage at all, unlike every other screen in the app.
19. **ZSB-19 (Medium — parity/i18n):** The web/PWA Classroom page is effectively 100% hardcoded English — `useTranslation` is only used to translate API error codes, never to render any visible copy.
20. **ZSB-20 (Medium):** The onboarding CAPTCHA helper (`getCaptchaToken`, on both Android and web) can hang forever if `window.grecaptcha` hasn't finished loading by submit time, because the optional-chaining call skips invoking `resolve` entirely.
21. **ZSB-21 (Low-Medium):** The Admin KYC "Save schedule" (Tier-3 physical verification) action has no `onSuccess`/`onError` handling at all — no cache refresh, no success or failure toast — so the admin gets zero confirmation the date/notes were actually saved.
22. **ZSB-22 (Low):** The Google/Telegram OAuth loading spinner on Login/Register resets the instant the in-app browser tab *opens*, not when OAuth actually completes, giving almost no protection against double-tapping the button mid-flow.
23. **ZSB-23 (Low — parity, self-documented):** The Android Friends screen has no "Recent chats" tab that the web version has, because the required i18n keys were never added.
24. **ZSB-24 (Low — ops):** The Android CI build workflow hardcodes an explicit branch allow-list (`on.push.branches`), so any new working branch (including this one) silently never triggers a build until someone edits the workflow.
25. **ZSB-25 (Low — UX nit):** `PullToRefresh`'s gesture only checks scroll position at `touchstart`; a gesture that starts mid-list and scrolls to the top mid-drag never arms the refresh indicator for that same touch.

## Detailed findings

### 1: ZSB-01: Registration OAuth callback still uses the insecure custom-scheme redirect
**FILES:** `apps/android/src/routes/auth/register.tsx` (line 15), compare `apps/android/src/routes/auth/login.tsx` (line 27), `apps/android/android/app/src/main/AndroidManifest.xml`
**FIX:** `login.tsx` was deliberately patched (see its own `BUG-CAP-04` comment) to use `` `${env.VITE_WEB_BASE_URL}/auth/callback` `` — the verified HTTPS Android App Link — specifically because a `zobia://` custom scheme can be registered by any other installed app, letting a malicious app race to intercept the OAuth exchange code. `register.tsx` still hardcodes `const CALLBACK_DEEP_LINK = 'zobia://auth/callback'`, so every new sign-up on Android still goes through the vulnerable path the login flow was fixed to avoid. Change `register.tsx` to build `CALLBACK_DEEP_LINK` from `env.VITE_WEB_BASE_URL` exactly like `login.tsx` does (ideally extract the shared constant into `lib/deeplinks/routes.ts` so the two screens can never drift again).

### 2: ZSB-02: Web/PWA Creator Dashboard crashes for every creator (field-name mismatch)
**FILES:** `apps/web/app/(app)/creator/page.tsx` (lines 336–415), `apps/web/app/api/creator/dashboard/route.ts` (lines 286–318). Compare the *correct* contract already implemented in `apps/android/src/routes/creator/index.tsx`.
**FIX:** The API route returns `revenue.week` / `revenue.month` / `revenue.byStream{...}` / `members.total` / `members.active` / `topGifters[].user_id`/`avatar_emoji`/`total_coins`, and has no `dailyRevenue`, `revenueStreams`, `totalMembers`, `activeMembersPct`, or `payoutBalance` fields at all. The web page instead reads `data.revenue.thisWeek`, `data.revenue.thisMonth`, `data.dailyRevenue`, `data.revenueStreams` (then calls `.map()` on it — an unguarded crash since it's `undefined`), `data.totalMembers`, `data.activeMembersPct`, `data.payoutBalance`, and `data.topGifters[].userId/avatarEmoji/totalGifted`. This is a hard runtime crash, not just a display glitch — every creator who opens `/creator` on web/PWA today gets a broken page. Rewrite the web page against the actual response shape (mirror what `apps/android/src/routes/creator/index.tsx` already does correctly), or add the missing fields server-side if product wants the richer `dailyRevenue`/`revenueStreams`/`payoutBalance` breakdown — but either the client or the server needs to change, not both independently. This is the single highest-priority fix in this report.

### 3: ZSB-03: Dead "unauthenticated" event system + stale cached token never cleared
**FILES:** `apps/android/src/lib/api/client.ts` (lines 41–53, 199–217), `apps/android/src/lib/auth/store.ts`, `apps/android/src/components/auth/AuthGuard.tsx`
**FIX:** `onUnauthenticated()`/`onUserUpdated()` are exported and the response interceptor calls `notifyUnauthenticated()` after a failed silent refresh — but nothing in the app ever calls `onUnauthenticated(...)` to subscribe (confirmed via full-codebase search). Worse, that same failure branch clears Preferences but never calls the already-exported `setCachedToken(null)`, so the in-memory `_cachedToken` keeps being attached to every subsequent request. Combined, a user whose refresh token has expired/been revoked never gets signed out or redirected to `/auth/login` — the UI still shows them as logged in (stale `user`/`token` React state) while every API call silently fails. Fix both halves: (a) call `setCachedToken(null)` in the 401-refresh-failed branch of `client.ts`, and (b) subscribe to `onUnauthenticated` once in `AuthProvider` (or `__root.tsx`) and call `clearAuth()` + navigate to `/auth/login` from it.

### 4: ZSB-04: "Open in browser" flows have no authenticated session
**FILES:** `apps/android/src/routes/kyc.tsx`, `apps/android/src/routes/ads/index.tsx`, `apps/android/src/routes/creator/bank-account.tsx`, `apps/android/src/routes/creator/wallet.tsx`, `apps/android/src/routes/games/$slug.tsx`, `apps/android/src/routes/games/saved.tsx`, `apps/android/src/routes/admin/users.tsx` (the "View KYC Submissions" button), `apps/web/app/api/auth/google/callback/route.ts` (mobile-flow branch, ~line 443)
**FIX:** I verified in the OAuth callback route that the "mobile flow" branch (triggered by a stored `zobia_mobile_redirect` cookie) deliberately redirects with a one-time exchange code and *never* sets the `accessCookie`/`refreshCookie` HttpOnly session cookies — those are only set in the separate "web flow" branch. That means the Chrome Custom Tab these screens open via `Browser.open(universalLink(...))` has no logged-in session with `zobia.org` at all (unless the user coincidentally has an unrelated, separately-established browser session). Tapping "Verify identity (KYC)", "Manage on web" (bank account/wallet), "View KYC Submissions", or "Resume"/"Play" on a game will simply present the web login page instead of the intended feature. Add a short-lived, single-use "mobile bridge" token: when opening one of these links, first call a new endpoint that mints a one-time code, then open `universalLink(path) + '?bridge=<code>'`; have the destination page exchange that code server-side for a normal web session cookie before rendering (same pattern the OAuth mobile-token exchange already uses, just applied to these authenticated hand-off links too).

### 5: ZSB-05: Push token never re-registers across an account switch on one device
**FILES:** `apps/android/src/lib/push/index.ts` (the `initialized` flag), `apps/android/src/lib/auth/store.ts` (`clearAuth`), `apps/web/app/api/users/push-token/route.ts`
**FIX:** `attemptInit()` short-circuits permanently once `initialized` is `true` (set the first time permission is granted). If User A logs out and User B logs in on the same device without a cold restart, `PushNotifications.register()` never fires again, so `registerToken()` (which POSTs the FCM token tied to *whichever* account is authenticated at call time) never runs for User B — the server-side `(user_id, token)` row from the push-token upsert stays pointed at User A. User B may get no push notifications, and any push meant for User A can still land on the device while User B is using it. Reset `initialized = false` inside `clearAuth()` (or re-derive it from the current user id), and add a `DELETE /api/users/push-token` (or similar) call on logout so the server-side association is actively removed, not just left stale.

### 6: ZSB-06: Ably realtime is disabled in every shipped Android build
**FILES:** `.github/workflows/android-build.yml` (both the `build` and `release` jobs' env blocks), `apps/android/src/lib/env.ts`, `apps/android/src/lib/realtime/useRealtimeChannel.ts`
**FIX:** `env.ts` defaults `VITE_REALTIME_PROVIDER` to `'none'` when unset, and the CI workflow's `env:` block for the Vite build step only forwards `VITE_API_BASE_URL`, `VITE_WEB_BASE_URL`, `VITE_APP_ENV`, and `VITE_DEBUG_OVERLAY` — `VITE_REALTIME_PROVIDER` is never referenced at all. That means every APK/AAB built by this workflow (debug and release) ships with realtime hardcoded off, so Rooms and DM chat always fall back to the slower adaptive poll instead of the instant Ably updates the web app gets. Add `VITE_REALTIME_PROVIDER: 'ably'` (sourced from a repo/environment variable, not a secret since it's not sensitive) to both jobs' env blocks in `android-build.yml`.

### 7: ZSB-07: 2FA login on Android never persists the refresh token
**FILES:** `apps/android/src/routes/auth/two-factor.tsx` (line 40), `apps/web/app/api/auth/2fa/verify/route.ts` (confirms `refreshToken` is present in the `?platform=mobile` response body)
**FIX:** `await setAuth(data.accessToken, data.user);` omits the third, optional `refreshToken` parameter even though the server's mobile response includes one. Every other login path in this app (the OAuth deep-link exchange in `__root.tsx`) does pass it through. Without a stored refresh token, `refreshAccessToken()` finds nothing in Preferences the moment the short-lived access token expires, so 2FA users get bounced back to login (and have to re-enter their 2FA code) far more often than non-2FA users. Change the call to `await setAuth(data.accessToken, data.user, data.refreshToken);`.

### 8: ZSB-08: `apiFetch.ts`'s 401 path silently drops the failed request with no cleanup
**FILES:** `apps/android/src/lib/api/apiFetch.ts` (lines 60–70)
**FIX:** When `refreshAccessToken()` fails inside `apiFetch`, the function just `return response;` (the original 401) with no call to clear the cached token, no Preferences cleanup, and no notification to the rest of the app — a second, divergent implementation of the same broken-session problem as ZSB-03, this time for the handful of calls that go through `apiFetch` instead of `apiClient` (currently just the presence heartbeat, but likely to grow). Once ZSB-03's fix exists, route this failure path through the same `notifyUnauthenticated()`/token-clearing logic instead of maintaining a second copy.

### 9: ZSB-09: Ad-event queue has an unguarded read-modify-write race
**FILES:** `apps/android/src/lib/ads/adEventQueue.ts` (`enqueueAdEvent`, `readQueue`/`writeQueue`)
**FIX:** `enqueueAdEvent()` fires an unawaited async IIFE that reads the current queue from `idb-keyval`, pushes the new event, then writes it back — with no lock. Two ad impressions logged in quick succession (a common case: a feed can render several `AdSlot`s that all become visible around the same time) can both read the same queue snapshot before either writes, so the second write clobbers the first — silently dropping an impression/click event. Serialize access with an in-memory promise chain/mutex (`let writeChain = Promise.resolve(); function enqueue(...) { writeChain = writeChain.then(async () => { ...read, push, write... }); }`) so pushes never race each other.

### 10: ZSB-10: Friend request accept/reject reads the wrong mutation variables
**FILES:** `apps/android/src/routes/friends.tsx` (`ReceivedRequestsList`'s `respondMutation`)
**FIX:** `onSuccess: (_res, { requestId }) => { ...; if (respondMutation.variables?.action === 'accept') qc.invalidateQueries(...) }` — the `if` reads the *shared hook's* `.variables`, which reflects whichever call was started most recently, not necessarily the one that just resolved. If a user accepts one request and declines another in quick succession, the two `onSuccess` firings can read each other's `.variables.action`, causing the friends list to wrongly skip a refresh after a real accept, or refresh needlessly after a decline. Destructure `action` from the callback's own second argument alongside `requestId` (`onSuccess: (_res, { requestId, action }) => { ...; if (action === 'accept') ... }`) instead of touching the shared hook state.

### 11: ZSB-11: Coin-spend actions don't invalidate the shared balance query
**FILES:** `apps/android/src/routes/gifts.tsx` (`closeModal`, only invalidates `['gifts','wallet']`), `apps/android/src/routes/stickers.tsx` (`unlockMutation`, only invalidates `['stickers']`), compare `apps/android/src/routes/wallet.tsx` (reads balance from `['users','me']`)
**FIX:** Sending a gift or unlocking a paid sticker pack spends coins server-side, but neither screen invalidates the `['users','me']` query that the Wallet screen (and anywhere else showing the coin balance) reads from. If a user spends coins then navigates to Wallet within the query's `staleTime` window, they'll see their pre-spend balance. Add `qc.invalidateQueries({ queryKey: ['users', 'me'] })` alongside the existing invalidations in both places (and audit any other coin/star-spending mutation for the same gap — this looks like a systemic pattern, not isolated to these two screens).

### 12: ZSB-12: Buying coins/stars doesn't refresh the transaction history list
**FILES:** `apps/android/src/routes/wallet.tsx` (`BuyCurrencyPanel`'s `handleBuy` → `onPurchased`)
**FIX:** `onPurchased` only calls `qc.invalidateQueries({ queryKey: ['users', 'me'] })`, updating the balance cards, but not the `['wallet', 'transactions', tab]` infinite query, so the just-completed Google Play purchase doesn't show up in the transaction history until something else happens to refetch it. Also invalidate `['wallet', 'transactions']` (both tabs, or at least the active one) in `onPurchased`.

### 13: ZSB-13: Referral code capture never expires on Android
**FILES:** `apps/android/src/lib/deeplinks/referral.ts`, compare `apps/web/lib/referral/clientStore.ts` (`TTL_DAYS = 30`)
**FIX:** The web/PWA client stores a captured `?r=` code in a first-party cookie with a 30-day `Max-Age` specifically so a very old, long-forgotten link tap doesn't misattribute a much-later organic signup. The Android version stores the same code in Capacitor `Preferences` with no expiry at all — `getPendingReferralCode()` will happily return a code captured a year ago. Store a captured-at timestamp alongside the code and have `getPendingReferralCode()` return `null` (and clear it) once it's older than the same 30-day window web uses, for consistent attribution behaviour across platforms.

### 14: ZSB-14: `applyStoredLanguagePref()` is fully implemented but never invoked
**FILES:** `apps/android/src/lib/i18n/index.ts` (function definition), `apps/android/src/main.tsx` (where it should be called)
**FIX:** This function exists specifically to restore the user's language choice from the more durable Capacitor `Preferences` store (native SharedPreferences) "to overlay the device-locale default" per its own docstring — a safety net for when the WebView's `localStorage` (which `i18next-browser-languagedetector` normally reads/writes) gets cleared independently of app data, e.g. via Android's "Clear cache" option. A repo-wide search confirms it is never imported or called anywhere. Call `await applyStoredLanguagePref()` once during boot in `main.tsx`, before (or right after) `i18n` initializes.

### 15: ZSB-15: Dead, unused `VITE_ABLY_API_KEY` env var
**FILES:** `apps/android/src/lib/env.ts` (schema + raw parsing)
**FIX:** This variable is validated and parsed into `env.VITE_ABLY_API_KEY` but never read anywhere else in the app (realtime auth correctly goes through the server-side `/realtime/ably-token` endpoint instead, which is the right pattern). Since Vite bundles every `VITE_`-prefixed environment variable directly into the client JS, if anyone ever "helpfully" wires this up directly against the Ably SDK later, it would ship a real API key into the public APK. Delete the field entirely now while it's unused, or add a loud comment forbidding its use for anything other than a placeholder, to stop this from becoming a real secret-exposure incident later.

### 16: ZSB-16: Notifications list has no tap-to-navigate behaviour
**FILES:** `apps/android/src/routes/notifications.tsx`, `apps/android/src/lib/notifications/queries.ts` (`Notification` interface has no route/URL field), compare `apps/web/app/(app)/notifications/page.tsx` (line 268, `href={notification.actionUrl}`)
**FIX:** Tapping a notification on Android only calls `markReadMutation.mutate([notification.id])` — it never navigates anywhere, unlike web which wraps each row in a link driven by `notification.actionUrl`. The push-notification tap handler (`lib/push/index.ts`) already has an allowlisted-route navigation pattern that could be reused here: extend the `Notification`/`NotificationsPayload` types to carry a route (derived from `type`/`metadata`, mirroring the server-side mapping used for push actions), and navigate through the same `isAllowedRoute`-style allowlist on tap.

### 17: ZSB-17: PWA has no Web Push implementation at all
**FILES:** `apps/web/app/sw.ts` (no `push` or `notificationclick` event listener anywhere in the service worker)
**FIX:** The Capacitor app registers for FCM push and handles foreground/background notification taps; the PWA's service worker has no equivalent `self.addEventListener('push', ...)`/`notificationclick` handling at all, so installed-PWA users never receive a background push notification regardless of what the backend sends. If background notifications for PWA users are in scope for parity, add Web Push (VAPID) support to `sw.ts` plus a subscription-registration flow analogous to `lib/push/index.ts`; if it's deliberately out of scope for now, document that decision so it doesn't get "rediscovered" as a bug later.

### 18: ZSB-18: Business Ads Hub + Business Pages screens are entirely unlocalized
**FILES:** `apps/android/src/routes/ads/index.tsx`, `apps/android/src/routes/business/ads/index.tsx`, `apps/android/src/routes/business/pages/index.tsx`, `apps/android/src/routes/business/pages/$pageId.tsx`
**FIX:** None of these four files import or call `useTranslation`/`t()` — every visible string ("Advertising Panel", "Ad Campaigns", "+ New Ad Campaign", feature descriptions, etc.) is a hardcoded English literal, unlike the rest of the app which is fully wired for the 9 supported locales (including RTL Arabic). A French/Arabic/Hausa/etc. user reaching these screens sees raw English mixed into an otherwise-translated app. Add the missing `business.ads.*`/`ads.hub.*`/`business.pages.*` keys to `shared/i18n/locales/*.json` (following the same key-naming convention already used elsewhere) and wire `useTranslation()` through these four files.

### 19: ZSB-19: Web/PWA Classroom page is hardcoded English despite having i18n keys available
**FILES:** `apps/web/app/(app)/classroom/page.tsx`, compare `apps/android/src/routes/classroom.tsx` (whose own header comment notes it added a full `classroom.*` namespace to `en.json` that the web page still doesn't use)
**FIX:** The web Classroom page imports and calls `useTranslation()` three separate times, but only to feed `translateApiError()` for error codes — every visible label/button/heading is a raw English string literal. Since the Android port already had to add the `classroom.*` i18n keys to make its own version correctly localized, the same keys are sitting unused in `shared/i18n/locales/*.json` — wire the web page's copy through `t('classroom.*', ...)` the same way Android's version does, instead of leaving the keys orphaned.

### 20: ZSB-20: Onboarding CAPTCHA can hang forever on a slow/late script load
**FILES:** `apps/android/src/routes/onboarding.tsx` (`getCaptchaToken`), also present in the mirrored `apps/web/app/onboarding/page.tsx` (`getCaptchaToken`)
**FIX:** `return new Promise((resolve) => { window.grecaptcha?.ready(async () => { ... resolve(...) }); })` — if `window.grecaptcha` is still `undefined` at call time (the script tag is still loading), the optional chaining short-circuits the whole `.ready(...)` call and `resolve` is never invoked. The returned promise never settles, so `handleSubmit`'s `await getCaptchaToken()` hangs indefinitely — the submit button stays stuck on "Submitting…" forever with no error and no way to recover short of leaving the screen. Add a timeout (e.g. `Promise.race([...,  new Promise(resolve => setTimeout(() => resolve(null), 8000))])`) so a slow/failed script load degrades to "no captcha token" (which the server can reject with a normal, recoverable error) instead of hanging the UI.

### 21: ZSB-21: Admin KYC "Save schedule" gives no feedback and doesn't refresh
**FILES:** `apps/android/src/routes/admin/kyc.tsx` (the `schedule` mutation inside `DetailOverlay`)
**FIX:** `schedule.mutate()` has no `onSuccess`/`onError` handler at all — unlike the `approve`/`reject` mutations right next to it, which call `onResolved` (closing the overlay + refetching the queue + showing a toast). After an admin schedules (or reschedules) a Tier-3 physical verification appointment, nothing on screen changes: the detail view's own `physical_verification_scheduled_at` field isn't refetched, and there's no success/error toast, so the admin has no way to tell whether the save actually worked. Add `onSuccess: () => qc.invalidateQueries({ queryKey: ['admin', 'kyc', 'detail', id] })` (and a toast, matching the `approve`/`reject` pattern) to the `schedule` mutation.

### 22: ZSB-22: OAuth loading state clears before the OAuth flow actually completes
**FILES:** `apps/android/src/routes/auth/login.tsx`, `apps/android/src/routes/auth/register.tsx` (`handleGoogleLogin`/`handleTelegramLogin`/etc., the `finally` blocks)
**FIX:** `setGoogleLoading(true)` is reset back to `false` in a `finally` block that runs as soon as `Browser.open(...)` *resolves* — which happens the instant the Custom Tab opens, not when the user finishes (or abandons) the OAuth flow in it. In practice the loading spinner is visible for well under a second, so there's essentially no protection against a user backgrounding the browser tab and tapping the same login button again, potentially stacking multiple Custom Tab instances. Consider tracking "OAuth in progress" via a longer-lived signal (e.g. cleared only when `__root.tsx`'s `appUrlOpen` handler fires or the app resumes foreground without a completed login) rather than resetting it as soon as the tab opens.
